# PhotoArchiver Code Review Rules

Version: 1.0.1

Status: Stable

Last Updated: 2026-07-24

---

# 1. Purpose

This document defines the code review standards for the PhotoArchiver project.

Every code change, whether written by a human or generated by AI, should be reviewed before being accepted into the project.

The objective of code review is to ensure:

* Correctness
* Maintainability
* Consistency
* Performance
* Readability
* Architectural integrity

---

# 2. Scope

These rules apply to:

* Python source code
* UI code
* Configuration files
* Documentation
* Tests
* Build scripts
* AI-generated code

---

# 3. Review Principles

Every review should answer the following questions:

1. Is the code correct?
2. Is the architecture respected?
3. Is the code easy to understand?
4. Is the implementation maintainable?
5. Is the solution consistent with project standards?

---

# 4. Review Workflow

Recommended review process:

```text
Code Completed
        │
        ▼
Static Analysis
        │
        ▼
Unit Tests
        │
        ▼
Architecture Review
        │
        ▼
Code Review
        │
        ▼
Documentation Review
        │
        ▼
Merge
```

---

# 5. Review Categories

Every review should evaluate:

* Architecture
* Dependency
* Naming
* Readability
* Performance
* Error Handling
* Thread Safety
* UI
* Security
* Documentation
* Testing

---

# 6. Severity Levels

## CRITICAL

Must be fixed before merge.

Examples:

* Data loss
* Crash
* Deadlock
* SQL corruption
* Thread safety violation
* Security issue

---

## MAJOR

Should be fixed before merge.

Examples:

* Architecture violation
* Wrong dependency
* Missing exception handling
* Missing validation
* Incorrect business logic

---

## MINOR

Improvement suggested.

Examples:

* Naming
* Formatting
* Readability
* Minor duplication
* Comment quality

---

# 7. Architecture Review

Verify:

* Correct project layer
* Correct module placement
* No forbidden imports
* No circular dependencies
* Repository pattern followed
* Worker pattern followed

Reference:

* architecture-rules.md
* dependency-rules.md

---

# 8. Business Logic Review

Confirm that:

* Business rules remain in Domain/Application
* UI contains no business logic
* Infrastructure contains no business decisions

---

# 9. UI Review

Verify:

* UI remains responsive
* Long-running tasks use Workers
* No UI updates from background threads
* Signals and Slots are used correctly
* Error messages are user-friendly

Reference:

* ui-rules.md
* worker-rules.md

---

# 10. Worker Review

Check:

* Runs outside UI thread
* Supports cancellation
* Emits progress updates
* Releases resources
* Handles exceptions
* Uses Loguru
* Does not manipulate widgets

---

# 11. Dependency Review

Verify:

* Domain has no framework dependencies
* Application uses interfaces
* Infrastructure implements interfaces
* Presentation does not import Infrastructure

Reference:

* dependency-rules.md

---

# 12. Code Style Review

Confirm:

* Ruff formatting passes
* Naming follows conventions
* No wildcard imports
* No unused imports
* No duplicated code
* Functions remain focused

---

# 13. Error Handling Review

Every expected failure should:

* Be handled
* Be logged
* Provide useful feedback

Avoid:

* Bare `except:`
* Silent failures
* Empty exception handlers

---

# 14. Logging Review

> **print 禁令/日志权威**：`.ai/rules/coding-rules.md` COD-050（用 Loguru）+ COD-051（禁 `print()`）。本节是 §22 Review 在日志层的细化，不重复 COD-050/051 正文。

Verify:

* Loguru is used
* No `print()` statements remain
* Logs are meaningful
* Sensitive information is not logged

---

# 15. Performance Review

Check for:

* Unnecessary loops
* Repeated database queries
* Repeated file access
* Excessive object creation
* Large memory allocations

Prefer efficient algorithms and batch operations where appropriate.

---

# 16. Database Review

Verify:

* SQL is isolated in Infrastructure
* Transactions are handled correctly
* Connections are released
* Repository pattern is respected

---

# 17. File System Review

Confirm:

* `pathlib.Path` is used
* Paths are validated
* Temporary files are cleaned up
* User data is not overwritten unintentionally

---

# 18. AI Review

AI-generated code must also be reviewed.

Review should verify:

* Correct architecture
* Correct dependencies
* Readable implementation
* No unnecessary complexity
* No invented APIs
* No placeholder logic in production code

AI-generated code is never exempt from review.

---

# 19. Documentation Review

When implementation changes:

Review whether updates are needed for:

* README.md
* docs/
* .ai/
* Configuration examples

Documentation should accurately reflect the current implementation.

---

# 20. Testing Review

Verify:

* New logic has tests where appropriate
* Existing tests still pass
* Edge cases are considered
* Regression risks are minimized

---

# 21. Security Review

Check for:

* Unsafe file operations
* Path traversal risks
* Injection vulnerabilities
* Unsafe deserialization
* Exposure of sensitive data in logs

Security concerns are always treated as **CRITICAL**.

---

# 22. Review Checklist

Before approving code, verify:

* [ ] Architecture rules respected
* [ ] Dependency rules respected
* [ ] UI rules respected
* [ ] Worker rules respected
* [ ] Naming is clear
* [ ] Error handling complete
* [ ] Logging implemented
* [ ] Tests pass
* [ ] Documentation updated
* [ ] No debug code
* [ ] No TODO placeholders in production code
* [ ] No commented-out obsolete code

---

# 23. Merge Criteria

A change is ready to merge when:

* No CRITICAL issues remain
* No MAJOR issues remain
* Tests pass
* Static analysis passes
* Documentation is updated (if required)
* Review checklist is complete

MINOR issues may be deferred if they do not affect correctness or maintainability.

---

# 24. Review Comments

Review comments should be:

* Specific
* Actionable
* Respectful
* Referenced to project rules when possible

Example:

```text
DEP-021:
Domain module imports OpenCV.
Move image processing into Infrastructure.
```

Avoid vague comments such as:

```text
This looks wrong.
```

---

# 25. Continuous Improvement

Common review findings should be incorporated into:

* Coding standards
* AI rules
* Architecture rules
* Project templates

The review process should improve the project over time.

---

# 26. Summary

Code review is a quality gate, not a formality.

Every change should improve the project or, at minimum, preserve its quality.

Following these rules ensures that PhotoArchiver remains:

* Stable
* Maintainable
* Consistent
* Scalable
* AI-friendly
