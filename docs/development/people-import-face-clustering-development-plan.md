# 人员名单导入与人脸分组匹配开发方案

## 1. 目标与现状

本方案把“名单导入 → 人脸分组 → 按拍摄时间给出名单配对建议 → 人工确认 → 后续识别复用样本”做成一条可回溯的流程。

现有实现的关键边界：

- `ImportPeopleService` 以固定四列、首行表头、一行一人为规则直接写入 `people`，没有导入预览或人工确认。
- 当前识别只处理每张照片中置信度最高的一张脸，并写入一条 `RecognitionResult`；没有人物分组。
- `person_embeddings` 没有人员样本登记入口，名单不能作为可识别的人脸候选集。
- `photos.captured_at` 已保存拍摄时间；当前识别结果和审核列表均未按它组织。

现有代码入口：

- 导入：`application/services/import_people_service.py`、`infrastructure/importers/`
- 人员：`domain/entities/person.py`、`infrastructure/database/sqlite_person_repository.py`
- 识别：`application/services/match_persons_service.py`、`ai/insightface_detector.py`
- 审核：`presentation/views/review_dialog.py`
- 删除：`application/services/delete_person_service.py`

## 2. 目标业务流程

```text
选择名单文件
  → 解析为导入草稿（保留原始内容、解析结果、告警）
  → 用户选择字段/处理拆分、重复和异常行
  → 确认后写入人员名单及名单顺序

扫描照片
  → 每张照片检测全部人脸，保存人脸观测和特征
  → 将人脸观测聚类为人物组
  → 人物组按最早有效拍摄时间升序排列
  → 按名单顺序生成“建议配对”
  → 用户确认、改配、合并、拆分或标记未知
  → 确认的组成为该人员的多张人脸样本

后续新增照片
  → 使用已确认人员样本识别
  → 对未知或低置信度人脸继续进入分组审核
```

时间顺序只用于生成建议，不能自动确认身份。人员归属必须经人工确认或达到后续单独定义的自动确认阈值。

## 3. 领域模型与状态

### 3.1 名单导入

新增以下持久化对象：

| 对象 | 主要字段 | 用途 |
| --- | --- | --- |
| `import_batches` | id、文件名、哈希、来源类型、创建时间、状态 | 一次导入的可追溯容器 |
| `import_draft_rows` | batch_id、源位置、原始值、解析字段、告警、处理动作、顺序 | 确认前的可编辑草稿 |
| `people.roster_order` | 整数 | 用户确认的名单顺序 |
| `people.source_batch_id` | 可空 FK | 人员来源追踪 |

`import_batches.status`：`draft`、`confirmed`、`cancelled`。

草稿行处理动作：`create`、`merge_existing`、`skip`。一条原始行可拆成多个草稿人员；疑似组标题可标记为 `skip`，不作为人员写入。

### 3.2 人脸与人物组

新增以下持久化对象：

| 对象 | 主要字段 | 用途 |
| --- | --- | --- |
| `recognition_runs` | id、算法版本、范围、状态、创建/完成时间 | 允许明确重跑，不再以“是否已有结果”阻止重分析 |
| `face_observations` | run_id、photo_id、bbox、检测/质量分、embedding、captured_at 快照 | 一张照片中的一张脸 |
| `face_clusters` | run_id、状态、first_captured_at、排序键 | 同一人物的人脸组 |
| `face_cluster_members` | cluster_id、observation_id、来源、置信度 | 组成员关系 |
| `cluster_person_assignments` | cluster_id、person_id、状态、来源、分数、确认时间 | 人物组和人员的可审计映射 |
| `person_face_embeddings` | person_id、observation_id、embedding、质量、启用状态 | 人员的多张已确认样本 |

保留现有 `recognition_results` 作为历史审批与归档兼容层。新流程确认映射后，由适配服务生成或更新兼容的正式归属；迁移期间不删除历史结果。

`face_clusters.status`：`pending`、`confirmed`、`unknown`、`ignored`、`split`、`merged`。

`cluster_person_assignments.status`：`suggested`、`confirmed`、`rejected`、`unassigned`。

## 4. 导入解析与确认规则

### 4.1 解析原则

- 支持 `.xlsx`、`.xlsm`、`.xls`、`.csv`、`.tsv`、`.txt`；不支持的文件在选择后明确提示，不把二进制内容按 CSV 解析。
- 先检测编码、分隔符、工作表和表头，再由用户确认；CSV/TXT 覆盖 UTF-8、UTF-16、GBK/GB18030 等常见编码。
- 字段映射不固定列序，至少支持姓名、工号、部门、备注、组别；允许仅提供姓名。
- 检测顿号、中文/英文逗号、分号、换行和连续空格等疑似多人分隔符，生成拆分建议，但不静默拆分。
- 识别形如“2组”“第 2 组”“名单”的单元格/行并提示为组标题；组别可保留为导入来源信息，不默认创建人员。
- 工号重复为强冲突；姓名+部门重复为弱冲突。二者均在预览中由用户决定合并、保留或跳过。

### 4.2 导入确认页

确认页按“原始内容 / 解析结果 / 告警 / 处理动作”展示草稿，支持：

- 修改字段、增加、删除、拆分、合并草稿人员；
- 批量设置列映射、分隔规则、工作表和表头；
- 查看将新增、合并、跳过的数量；
- 最终确认后在一个事务中写入人员及稳定的 `roster_order`；
- 取消时不改变正式人员名单，草稿可保留供继续编辑。

导入完成后进入“人员名单管理”页。该页提供新增、编辑、删除、拖拽调整名单顺序和按批次回看来源。删除沿用当前安全语义：照片和磁盘文件不删除，已有关联转为未分配。

## 5. 人脸检测、分组与时间排序

### 5.1 检测

- 识别任务改为对每张照片保存全部检测到的人脸，而非只选择最高置信度人脸。
- 每个人脸记录边界框、检测分、质量分、嵌入特征和照片拍摄时间快照。
- 不可读取、无人脸、低质量照片分别计数并可在界面筛选；不可读取不能伪装成无人脸。
- 继续使用当前 Unicode 路径安全的读图路径。

### 5.2 聚类

- 对同一 `recognition_run` 中的人脸嵌入做批量聚类，先按相似度形成候选，再以组内一致性约束合并，避免相似度链式误合并。
- 低质量或边界分数的人脸可作为候选，但不能单独推动两个组自动合并。
- 聚类参数与算法版本写入 `recognition_runs`；重跑不会覆盖历史审核结果。
- 提供人工“合并组”和“拆分组”。拆分后的成员关系与操作来源必须可追溯。

### 5.3 排序

人物组排序键为：

```text
(最早非空 captured_at, 最早照片的稳定路径键, cluster_id)
```

- `captured_at` 非空的组按时间升序；无拍摄时间的组统一排在最后。
- 缺失拍摄时间不得使用照片注册时间替代；界面明确标记“时间缺失，顺序建议不可靠”。
- 每次确认映射保存当时的排序快照；以后补入更早照片时，不回写已确认的人员映射。

## 6. 人物组与名单配对

配对工作台中，人物组按第 5.3 节排序，人员按 `roster_order` 排序。系统先生成建议，再由用户确认。

建议生成顺序：

1. 优先使用已确认人员样本的高置信度匹配；
2. 排除已明确拒绝的映射；
3. 对剩余人物组和剩余人员，按排序位置一对一生成建议；
4. 建议状态均为 `suggested`，不改变正式归属。

| 情况 | 默认结果 |
| --- | --- |
| 组数 = 人数 | 全部生成顺序建议，等待确认 |
| 组数 < 人数 | 仅对前 `min(组数, 人数)` 个生成建议；其余人员标记“尚无照片组” |
| 组数 > 人数 | 仅生成可配数量的建议；剩余组标记“未知/待处理” |
| 没有组 | 展示无人脸、读取失败、低质量统计；不生成归属 |
| 没有名单 | 允许先聚类；后续导入名单后再进入配对 |
| 人员被拆成多个组 | 提示相似组，支持合并或分别关联同一人员 |
| 多人误合并为一个组 | 支持按成员拆分后重新排序和配对 |

工作台必须支持：确认建议、替换人员、解除映射、将多个组关联同一人、合并组、拆分组、新增人员、标记陌生人、忽略组，以及查看每组的人脸缩略图和拍摄时间轴。

确认人员映射时，从该组选择合格样本写入 `person_face_embeddings`；后续 1:N 匹配基于多样本或中心特征，而不是现有单条 `person_embeddings` 覆盖式写入。

## 7. 分阶段实施与验收

每个阶段独立提交、迁移、测试和验收；下一阶段只依赖前一阶段已验收的接口。

### 阶段 A：导入草稿与稳定名单顺序

**范围**

- 新增导入批次、草稿行和人员名单顺序的 schema/migration。
- Reader 输出草稿数据；实现编码/分隔符/工作表/表头/字段映射选择。
- 提供导入预览、编辑、拆分、跳过和确认提交。

**验收**

- 当前标准 Excel/CSV 导入结果不回归。
- 顿号串联姓名可在预览中拆为多名人员。
- “2组”等行默认告警且可跳过。
- 取消导入不写正式人员；确认后名单顺序与预览一致。

### 阶段 B：人员名单管理

**范围**

- 新增人员、编辑人员、批量删除、调整顺序和导入来源查看。
- 复用现有删除预览及其照片保留语义。

**验收**

- 可手工补充、修改、删除人员，调整顺序后重启应用仍稳定。
- 删除人员后照片不删，历史归属变为未分配并可重新关联。

### 阶段 C：多脸检测与可重跑识别

**范围**

- 新增识别运行、人脸观测及其 migration。
- 改造检测管线，保存每张照片的全部人脸与失败分类。
- 增加“重新分析选中照片/全部照片”入口。

**验收**

- 多人合照产生多条人脸观测。
- 无脸、无法读取、低质量分别可统计。
- 历史识别记录不会阻止新运行；旧结果仍可查看。

### 阶段 D：人物聚类与时间排序

**范围**

- 实现人物组、成员关系、聚类任务和组列表。
- 实现按 `captured_at` 的稳定排序和时间缺失提示。
- 实现人工合并/拆分组。

**验收**

- 同一人跨多照片形成同一组；多人合照中不同人可分组。
- 有效拍摄时间最早的组排在前，无时间组排末。
- 合并/拆分后成员、排序和审计记录正确。

### 阶段 E：名单配对工作台与样本沉淀

**范围**

- 实现组—人员建议、确认、改配和未分配状态。
- 实现组数/人数不等场景的界面和操作。
- 实现多样本人脸库及后续照片的候选匹配。

**验收**

- 覆盖组数等于、小于、大于人员数的完整操作流程。
- 顺序建议不自动写正式归属；确认后才生效。
- 新照片可优先匹配已确认人员样本，低置信度仍进入人工队列。

### 阶段 F：历史数据、性能与上线

**范围**

- 将现有人员建立为历史导入批次并补齐稳定顺序。
- 提供历史照片重新分析入口和进度/失败报告。
- 在真实样本集上校准聚类及匹配阈值，补充日志和统计。

**验收**

- 升级既有数据库不丢失人员、照片、归档与历史审核数据。
- 千级照片任务可取消、重试、续跑；失败照片有明确清单。
- 完成端到端回归：导入、人工确认、识别、聚类、配对、审核、归档。

## 8. 测试清单

- Reader：编码、分隔符、无表头、多工作表、`.xls`、顿号名单、组标题、空行、重复工号。
- 导入草稿：拆分/合并/跳过、取消、确认原子性、名单顺序持久化。
- 识别：中文路径、不可读取、无人脸、多人合照、重复运行、取消与重试。
- 聚类：同人合并、异人分离、低质量边界、人工合并/拆分、稳定排序。
- 配对：组数与人数的所有关系、缺失拍摄时间、人员删除/新增、确认与撤销。
- 数据库：迁移升级、外键级联、历史数据兼容、事务回滚。
- UI：导入预览、人员管理、分组工作台、缩略图与时间轴、批量确认。

## 9. 实施约定

- 保持现有分层：Presentation → Application → Domain → Infrastructure；UI 不直接操作仓储。
- 所有新增 schema 通过 Alembic migration 落地，并为现有 SQLite 库提供升级路径。
- 识别、聚类和批量导入均在 Worker 中运行；人员编辑、单组确认可保持同步。
- 对无法可靠推断的文件内容或身份，只给建议与告警，保留人工决定入口。
